# RAPS Codebase Review — 2026-03-07

Comprehensive review of architecture, security, error handling, code quality, test coverage,
performance, documentation, and APS API coverage. Produced by direct codebase analysis of
commit `6b64793` (v5.4.0).

---

## 1. Architecture

### Crate dependency graph

```
raps-kernel   (foundation — no internal deps)
    ↑
    ├── raps-oss        (OSS: buckets, objects, multipart, range reads)
    ├── raps-dm         (Data Management: hubs, projects, folders, items)
    ├── raps-da         (Design Automation: engines, activities, appbundles, workitems)
    ├── raps-acc        (ACC: issues, RFIs, admin, assets, checklists, submittals)
    ├── raps-derivative (Model Derivative: translations, metadata, download)
    ├── raps-webhooks   (Webhook subscriptions and events)
    ├── raps-reality    (Reality Capture photogrammetry)
    └── raps-admin      (Bulk user operations — not workspace-declared but dep'd by raps-cli)
            ↑
        raps-cli        (top-level binary, depends on all service crates)
```

**Strengths:**
- Perfectly clean layering — no service crate depends on another service crate, only on `raps-kernel`. No circular dependencies.
- `raps-kernel` cleanly encapsulates all cross-cutting concerns: HTTP client, auth, caching, logging, rate limiting, security utils, error types, progress bars.
- Feature-gated optional dependencies (`redis`, `kubernetes`, `h3`) keep the default binary lean.

**Issues:**
- `raps-admin` is listed in `[workspace.dependencies]` (Cargo.toml:37) but absent from `[workspace.members]`. It compiles only because `raps-cli` adds it as a path dep. This is misleading — add it to `members` or remove it from workspace deps.
- `pipeline.rs` is 2,445 lines — the largest single file. The `--resume`, `--reset-from`, `--diff`, validation, and DAG logic should be split into `pipeline/run.rs`, `pipeline/state.rs`, `pipeline/dag.rs`, `pipeline/diff.rs`.
- `raps-cli/src/commands/mod.rs` functions as a large dispatch table. As the command set grows, consider splitting into feature modules with their own `mod.rs`.

## 2. Security

### Strengths

**Credential redaction in all log output** (`raps-kernel/src/logging.rs`):
Six patterns cover: `client_secret`, API keys, `Authorization: Bearer/Basic` headers, `Cookie`/`Set-Cookie`, `X-API-Key`, and URL query params (`?access_token=`, `?apikey=`). Redaction wraps both the stderr layer and the async file appender — no path to accidentally log a token.

**Path traversal protection** (`raps-kernel/src/security.rs`):
`sanitize_filename` strips `..`, NUL bytes, control chars, and takes only the terminal filename component. `safe_join` wraps it with a canonicalize check on the parent. `validate_path_within` confirms the target is under `base_dir`.

**Resource ID validation** (`security.rs:103`):
`validate_resource_id` rejects query-injection chars (`?`, `&`, `=`, `#`, `@`), control chars, and double-encoded sequences (`%2e`, `%2f`, `%00`, `%25`, `%0a`, `%0d`, `%09`). Applied to bucket keys and project IDs before URL interpolation.

**Prompt injection defense** (`security.rs:154`):
Eight regex patterns detect prompt injection in API responses before they reach MCP tool outputs. Applied via `strip_prompt_injection` on all JSON values recursively.

**Restricted directory permissions** (`security.rs:134`):
`create_dir_restricted` sets mode `0o700` on Unix using `DirBuilder::mode()` — atomically, avoiding a TOCTOU window between `create_dir_all` and `chmod`.

### Issues

**Multiple raw `reqwest::Client::new()` calls bypass the configured client**
(`commands/doctor.rs:363`, `doctor.rs:673`, `doctor.rs:894`, `commands/demo.rs:554`, `commands/job.rs:211`, `commands/webhook.rs:643`, `webhook.rs:892`).
These clients skip: TLS verification settings, HTTP/2 adaptive window, proxy configuration (`RAPS_PROXY`), and timeout from `HttpClientConfig`. They also bypass the `RedactingMakeWriter` for request logging. All should use `HttpClientConfig::default().create_client()`.

**`safe_join` TOCTOU on non-existent target**
When the joined path does not yet exist, `safe_join` only canonicalizes the parent, not the full path. A symlink attack placing a symlink at the parent before creation is not fully mitigated. Consider using `Path::new(base).join(sanitize_filename(name)?)` without canonicalize for non-existent targets — the filename is already sanitized.

**`ExitCode::from_error` uses string matching as fallback**
`error.rs:114`: The fallback scans error message strings for tokens like `"must be"`, `"404"`, `"timeout"`. An API error message containing these words gets misclassified. The `RapsError` enum should be used consistently; the string-matching fallback should be removed or heavily guarded.

## 3. Error Handling

### Strengths

- `RapsError` enum with `exit_code()` maps to semantic exit codes (0 success, 2 args, 3 auth, 4 not found, 5 remote, 6 internal). This is well-tested (rstest cases in `error.rs`).
- `interpret_error` parses APS error bodies and generates human-readable explanations + actionable suggestions per status code.
- `?` propagation with `anyhow::Context` is used consistently across service crates.

### Issues

**Silent `let _ =` discards in logging init** (`logging.rs:163`):
`let _ = tracing_subscriber::registry()...try_init()` silently succeeds or fails. The second call (e.g. in tests) fails silently — acceptable. But in production the first call should never fail; add a `panic!` in debug builds or log to stderr.

**`response.text().await.unwrap_or_default()` in `RapsError::from_response`** (`error.rs:54`):
If the response body stream errors (e.g. partial response), the error detail is silently dropped. Use `.unwrap_or_else(|e| format!("<body read failed: {e}>"))` to preserve the context.

**798 `.unwrap()`/`.expect()` calls in production code**:
Most are justified (regex compilations with `expect("regex is valid")`). However, a sampling shows some in command handlers that should propagate with `?`:
- `commands/doctor.rs:1019`: `std::fs::set_permissions(...).unwrap()` in a non-test function
- `commands/pipeline.rs:499,564`: `sem.acquire().await.expect("semaphore closed")` — a closed semaphore would panic; use `?` after converting `AcquireError`.

**`#[allow(dead_code)]` on public API surface**:
`ApsErrorResponse`, `InterpretedError`, `ResultExt`, `format_interpreted_error` are all `#[allow(dead_code)]`. These structs are part of a useful public API — wire them into the error display path or remove them.

## 4. Code Quality

### Strengths

- Consistent command structure: every command file defines a `pub async fn run(args, config, format)` entry point, making the dispatch table in `main.rs` uniform.
- Tracing spans on every HTTP request and command invocation enable production debugging with structured logs.
- `raps-kernel` provides shared utilities (progress bars, prompts, output formatting) that prevent duplication across commands.

### Issues

**Blocking std::fs I/O in async context**
The following use synchronous filesystem calls inside `async fn`s on the tokio thread pool, which can starve other tasks:

| File | Line | Call |
|------|------|------|
| `commands/lint.rs` | 126, 197, 398 | `std::fs::read_dir`, `read_to_string` |
| `commands/admin/mod.rs` | 579 | `std::fs::read_to_string` |
| `commands/logs.rs` | 53, 75, 135 | `std::fs::read_dir`, `read_to_string` |
| `commands/webhook.rs` | 731, 915 | `std::fs::File::open`, `std::fs::write` |

Replace with `tokio::fs::read_to_string`, `tokio::fs::read_dir`, `tokio::fs::write`.

**`pipeline.rs` god file** (2,445 lines):
Contains DAG topological sort, YAML parsing, step execution, retry logic, state persistence, diff, and validation. Split into `pipeline/dag.rs`, `pipeline/state.rs`, `pipeline/run.rs`, `pipeline/diff.rs`.

**846 `.clone()` calls**:
Many are necessary (sharing `Arc<Client>` across async tasks). The most avoidable pattern is cloning `String` arguments in commands where `&str` would suffice. A targeted audit of the 50 highest-frequency clone sites would be worthwhile.

**`reqwest::Client::new()` in 7 places**:
Creates throwaway unauthenticated clients. See Security section.

## 6. Performance

### Strengths

- `sync.rs`: parallel uploads via `tokio::task::spawn` + `Arc<Semaphore>` with configurable concurrency — good.
- `object/download_bulk.rs`: parallel downloads with semaphore — good.
- `raps-kernel/src/http.rs`: HTTP/2 adaptive window enabled by default for all APS API calls.
- Response cache with per-endpoint TTLs in `response_cache.rs` — reduces repeated GET calls.
- Adaptive multipart chunk sizing based on throughput measurement — smart.
- Rate-limit awareness with auto-sleep before 429 — prevents CI failures.

### Issues

**`sync.rs:151`: `list_objects` single blocking call**
All remote objects are fetched sequentially before the sync loop begins. For buckets with tens of thousands of objects, this is a serial bottleneck. APS OSS supports pagination — use concurrent page fetches or at minimum stream the list while uploading begins.

**`sync.rs:336`: sequential deletions**
```rust
client.delete_object(&args.bucket, key).await?;
```
Deletions run one at a time in a loop. Parallelize with the same semaphore pattern used for uploads.

**`pipeline.rs`: no timeout on individual steps**
Steps run with exponential backoff retries but no overall step timeout. A hung external command in a pipeline step will block forever. Add a `tokio::time::timeout` wrapping each step execution.

**`logs.rs:75`: `read_to_string` for `Show` command**
For `raps logs show --lines 50`, the entire log file is read into memory before taking the tail. Use `BufReader` + line counting from the end, or `tokio::fs::File` with seek.

## 7. Documentation

### Strengths

- `raps-kernel/src/http.rs` has excellent module-level doc comments covering H2, H3, configuration, and env vars.
- `security.rs` functions are thoroughly documented.
- `error.rs` has a clear exit code table in the module doc.

### Issues

**33 env vars used in code; only ~10 documented in `--help`**
The following are read from env but have no `--help` visibility or documentation page:

| Env Var | Effect |
|---------|--------|
| `RAPS_BASE_DELAY` | Base retry delay |
| `RAPS_MAX_WAIT` | Max retry wait |
| `RAPS_MAX_RETRIES` | Max retry count |
| `RAPS_TIMEOUT` | HTTP timeout |
| `RAPS_CONCURRENCY` | Default concurrency |
| `RAPS_DEVICE_PROXY_URL` | Device flow proxy |
| `RAPS_GATEWAY_URL` | Swarm gateway |
| `RAPS_GATEWAY_API_KEY` | Swarm gateway auth |
| `RAPS_USE_FILE_STORAGE` | Force file token storage |
| `RAPS_USE_KEYCHAIN` | Force keychain storage |
| `RAPS_STRICT` | Fail on warnings |
| `RAPS_NON_INTERACTIVE` | Disable prompts |
| `RAPS_QUIC_INSECURE` | Accept self-signed TLS for QUIC |
| `RAPS_SWARM_QUIC` | Enable QUIC transport |
| `RAPS_HTTP2` | Disable HTTP/2 (`=0`) |
| `RAPS_FILE_FORMAT` | File log format (`json`/plain) |

**Recommendation**: Add an `raps env` command that prints all env vars with descriptions, or add an `Environment Variables` section to the `--help` output of each relevant command.

**`#[allow(clippy::uninlined_format_args)]` at top of `main.rs`**:
This suppresses a style warning for all of `main.rs`. The `uninlined_format_args` lint was stabilized in Rust 1.65. With edition 2024 at Rust 1.88, these should be fixed rather than suppressed.

**`raps-reality/src/lib.rs` missing doc comments**:
The Reality Capture crate has no module-level documentation describing supported workflows or API endpoints.
